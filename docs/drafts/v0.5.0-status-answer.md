# v0.5.0 설계 초안 — `lg status`, `lg answer`

> 상태: 초안 (검토 중). 확정되면 [labgate-design.md](../../labgate-design.md)에 병합하고 이 파일은 지운다.
> 전제: v0.4.1 (`main` fc9b49e, spec_version 4). 마이너 버전이다.
> 명령 이름(`answer`)은 §8의 결정 1에서 정한다. 이 문서는 추천안으로 쓴다.

## 1. 목적

`lg init` 이후에도 사람이 **터미널 두 개(`lg`와 Claude Code)만으로** 연구를 진행할 수 있게 한다. 이를 위해 사람이 판단해야 할 일을 찾고, 읽고, 답하는 과정을 명령으로 만든다.

### 1.1 지금의 불편 (실사용, ssm-latent-reasoning M0-T0 게이트)

| 불편 | 원인 |
|---|---|
| 무엇을 판단해야 하는지 알려면 `reviews/open/`, `STATUS.md`, 카드를 직접 열어야 한다 | 판단 대기 목록을 사실에서 모아 주는 도구가 없다. `STATUS.md`는 에이전트가 쓰는 문서다 |
| 같은 판정을 두 번 쓴다: 요청서 `## 응답`에 글로, `lg commit`에서 trailer로 | 응답 문서와 커밋 trailer를 따로 만든다. 둘이 어긋나도 아무도 모른다 |
| 다음 task 넷(M0-T1–T4)을 함께 승인하고 싶은데 `Next`에는 하나만 쓸 수 있다 | 나머지는 따로 `plan`+`Approve` 커밋을 만들어야 한다는 것을 사람이 알아야 한다 |
| "M0 active 전환에 `plan` 커밋이 필요하다"는 에이전트의 틀린 안내를 걸러 낼 수 없었다 | 판정이 어떤 상태 변화를 만드는지 판정 전에 보여 주는 곳이 없다 |
| 카드의 완료 기준이 0/7 체크로 나온다. 요청서 표에는 모두 ✓다 | 절차 task-gate에 카드 체크 단계가 없다 |

### 1.2 v0.5.0이 하는 일

| 명령 | 누가 | 하는 일 |
|---|---|---|
| `lg status` | 사람, 에이전트 (읽기만) | 판단 대기, 사람 커밋 대기, 에이전트 반영 대기, 진행 중인 task를 파일과 이력에서 모아 보여 준다 |
| `lg answer [ID]` | 사람 (터미널에서만) | 열린 review를 터미널에 보여 주고, 판정을 한 번 묻고, 다음 세 가지를 **한 번에 만든다**: `## 응답`, frontmatter, `gate`/`respond` 커밋(+ 필요하면 `plan` 커밋). 판정이 만들 상태 변화를 먼저 보여 준다 |

요청서를 편집기로 직접 쓰는 길(문서 경로)과 터미널 B에서 말하는 길(대화 경로, 절차 gate-conversation)은 그대로 둔다. `lg answer`는 세 번째 길이고, 안내는 이것을 기본으로 한다.

## 2. 원칙

- **사실에서 모은다.** `lg status`는 `STATUS.md`를 읽지 않는다. frontmatter, `.lg/pending/`, 커밋 이력에서 계산한다. `STATUS.md`의 "사람 판단 대기"는 에이전트의 서술로 남는다.
- **규칙의 원본은 프로젝트다** (§23.3과 같다).
  - 판정이 만들 상태 변화는 프로젝트의 `scripts/apply-human-commits`가 계산한다(§5.4).
  - 커밋 규약은 프로젝트의 hook을 따른다.
- **`## 응답`은 사람만 쓴다 (G5).** `lg answer`는 `lg commit`처럼 표준 입력·출력이 모두 터미널일 때만 쓴다. 그래서 에이전트는 실행할 수 없다(Claude Code deny도 더한다). 응답은 사람의 손으로 쓰였다는 것을 도구가 보장한다.
- **사람이 우선이다.** 사람이 이미 손댄 응답이나 stage는 덮어쓰지 않는다. 멈추고 알린다.

## 3. `lg status`

### 3.1 형식

```
lg status [--json]
```

읽기만 한다. 사람과 에이전트 모두 실행할 수 있다. 종료 코드는 0이다. 프로젝트가 아니면 2.

### 3.2 출력

```
ssm-latent-reasoning · spec_version 5 · M0 (active)

사람이 할 일 2건
  [gate]  M0-T0_gate-01  M0-T0 착수 계획 · 10-03 요청      → lg answer M0-T0_gate-01
  [초안]  .lg/pending/COMMIT_MSG  exp: add loader           → lg commit

에이전트 몫 (다음 세션에서 자동)
  반영 대기 1건  gate(M0-T0): approve, next M0-T1 (3f2a1c9)

진행
  in-review  M0-T0 착수 계획
  draft      M0-T1–T5 (5)
  결정       proposed 5 (D0.1 D1.1 D2.1 D2.2 D3.1)
```

| 묶음 | 항목 | 출처 | 안내 |
|---|---|---|---|
| 사람이 할 일 | 열린 gate·escalation review (`status: open`) | `reviews/open/*.md` frontmatter | `lg answer <ID>` |
| | 응답은 썼지만 커밋 전 (`status: answered`이고 커밋되지 않음) | frontmatter + `git status` | `lg commit` |
| | 사람 커밋 대기 (초안) | `.lg/pending/COMMIT_MSG` | `lg commit` |
| | 커밋되지 않은 사람의 변경 | `.lg/pending/HUMAN_FILES` (없으면 `git status`) | `lg commit` |
| 에이전트 몫 | 반영되지 않은 사람 커밋 | 프로젝트의 `scripts/apply-human-commits --check` (spec_version 3 이상) | 다음 세션에서 자동 |
| | 반영했지만 커밋 전 | `.lg/pending/APPLY_MSG` | 다음 세션에서 자동 |
| 진행 | 현재 마일스톤과 상태, 상태별 task, proposed·discussing 결정 수 | frontmatter | — |

- 비어 있는 묶음은 한 줄("없음")로 줄인다.
- 사람이 할 일이 하나도 없고 에이전트 몫만 있으면 마지막 줄에 "에이전트 세션을 시작하면 이어서 진행합니다"를 쓴다.
- `--json`은 같은 내용을 기계가 읽는 형식으로 낸다. 에이전트의 세션 시작 보고나 다른 도구가 쓴다.

## 4. `lg answer`

### 4.1 형식

```
lg answer [REVIEW_ID] [--no-tag]
```

- `REVIEW_ID`를 생략했을 때:
  - 열린 review가 하나면 그것을 쓴다.
  - 여럿이면 목록에서 고른다.
  - 없으면 "열린 review가 없습니다"를 출력하고 코드 3.
- 전제는 `lg commit`과 같다(§18.3). 추가로 다음을 확인한다.

| 확인 | 실패 시 |
|---|---|
| 사람 커밋 대기 상태가 아니다 (`.lg/pending/COMMIT_MSG` 없음) | 코드 3. 대화 경로로 이미 초안이 있으면 `lg commit`으로 확정하라고 안내 |
| 그 review에 커밋되지 않은 변경이 없다 | 코드 3. 사람이 이미 응답을 쓰고 있다. 그대로 `lg commit`하라고 안내 (덮어쓰지 않는다) |
| review 외의 stage된 변경이 없다 | 코드 2 (`lg draft`와 같은 이유: 사람 커밋에 다른 변경이 섞이지 않게) |
| review의 `status`가 `open`이다 | `answered`면 코드 3과 `lg commit` 안내, `closed`면 코드 3 |

### 4.2 흐름

1. **보여 주기.** review를 터미널에 렌더링한다(rich Markdown, typer와 함께 이미 설치됨). 응답 위의 에이전트 섹션 전부를 보여 준다.
   - gate면 `lg verify --task <Task>`의 요약 한 줄(§23.5와 같은 것)과 카드의 완료 기준 체크 수를 덧붙인다.
   - 길면 pager로 보여 준다(`git`과 같은 규칙: `GIT_PAGER`, `core.pager`, `PAGER`, 없으면 `less -R`).
2. **묻기.** 4.3, 4.4의 질문.
3. **미리보기** (§5.4). 이 판정이 반영되면 생기는 일:
   ```
   이 판정이 반영되면 (다음 세션에서 에이전트가):
     M0-T0  in-review → closed
     M0-T1  draft → approved     (Next)
     M0-T2, M0-T3, M0-T4  draft → approved   (plan 커밋)
     M0     planned → active     (T0 승인)
     reviews/open/M0-T0_gate-01.md → reviews/closed/
   tag: gate/M0-T0
   ```
4. **확인.** 응답 원문과 커밋 메시지를 보여 주고 고른다: 커밋 / 편집기로 응답 수정 / 취소.
   - 편집기로 고친 응답도 다시 검사한다(판정 하위 섹션이 비어 있지 않은지).
   - 취소하면 아무것도 바뀌지 않는다. 확인 전에는 파일을 쓰지 않는다.
5. **쓰기와 커밋.**
   - review의 `## 응답` 하위 섹션을 채운다.
   - frontmatter를 고친다: `status: answered`, `answered: <오늘>`, `verdict`(gate), `source: document`, `updated`.
   - review 하나만 stage하고 `gate` 또는 `respond` 커밋을 만든다(사람 신원, hook 통과).
   - 다음 task를 여럿 골랐으면 이어서 빈 `plan` 커밋을 만든다(§4.3 결정 2).
   - gate 승인이면 tag를 만든다(`--no-tag`면 생략). `lg commit`과 같은 코드를 쓴다.
6. **안내.** `lg commit`의 커밋 뒤 안내(§18.2 9)와 같다: "다음 세션 시작 때 에이전트가 자동으로 반영합니다. 열린 세션에서 바로 이어 가려면 알리세요."

두 번째 커밋(`plan`)이 실패하면 첫 커밋은 그대로 두고 코드 4로 끝낸다. 남은 승인을 `lg commit`으로 하는 방법(`plan`, Approve 선택)을 안내한다.

### 4.3 gate 질문

| # | 질문 | 선택지·기본값 | 응답에 쓰는 곳 | trailer |
|---|---|---|---|---|
| 1 | 판정 | approve / revise / redirect | `### 판정` | `Verdict` |
| 2 | 다음 task (approve일 때) | 같은 마일스톤의 `draft` 카드를 여러 개 선택. 요청서의 `proposed_next`를 미리 골라 둔다. 고르지 않으면 "없음" | `### 다음 task 승인` | 첫째(`proposed_next`가 있으면 그것)는 `Next`, 나머지는 이어지는 `plan` 커밋의 `Approve`. 없으면 `Next: none` |
| 3 | 마일스톤 판정 (approve이고, 이 task와 고른 다음 task 말고는 그 마일스톤에 닫히지 않은 task가 없을 때만) | 하지 않음 / go / nogo / conditional | `### 판정`에 한 줄 더함 | `Milestone-Verdict` |
| 4 | 확정할 결정 | 요청서 `decisions`의 ID를 미리 골라 둔 목록. 그 밖의 proposed·discussing 결정도 고를 수 있다. 고른 결정마다 확정 내용 한 줄 | `### 확정 결정` | `Decisions` |
| 5 | 코멘트 | 한 줄 입력, 또는 편집기. revise·redirect면 필수(무엇을 고치거나 바꿀지) | `### 코멘트` | — |

- 커밋 헤더: `gate(<Task>): <verdict>` + (`, next <Next>`). 72자를 넘으면 `, next …`를 뺀다.
- trailer: `Actor: human`, `Task`, `Verdict`, `Source: document`, `Review: <ID>`, 그리고 고른 것.
- `Review` trailer는 지금도 hook이 허용하고, `apply-human-commits`가 이것으로 닫을 review를 찾는다.

### 4.4 escalation 질문

| # | 질문 | 선택지 | 응답 | trailer |
|---|---|---|---|---|
| 1 | 선택 | 요청서 `## 선택지`의 항목(제목 줄이나 목록의 첫 줄) + "직접 입력". 항목을 읽을 수 없으면 직접 입력만 | `### 판정` | — |
| 2 | 확정할 결정 | gate의 4와 같음 | `### 확정 결정` | `Decisions` (respond 커밋에도 쓸 수 있는지는 §8 결정 4) |
| 3 | 코멘트 | 한 줄 또는 편집기 | `### 코멘트` | — |
| 4 | 요약 | 기본값은 고른 선택지의 첫 40자 | — | 헤더 `respond(<Task>): <요약>` |

- trailer: `Actor: human`, `Task`, `Source: document`, `Review: <ID>`.
- `### 다음 task 승인`은 "없음"으로 쓴다.

## 5. 생성되는 프로젝트의 변경 (spec_version 5)

`lg status`와 `lg answer`는 지금의 review 양식과 trailer만으로 만들 수 있다. 다만 아래 넷은 생성되는 파일을 바꿔야 해결되므로 spec_version을 5로 올린다(범위는 §8 결정 2). v0.4.0의 `lg upgrade`로 기존 프로젝트도 올릴 수 있다.

### 5.1 절차 task-gate: 카드 체크와 사전 확인

- 1단계 뒤에 더한다:
  - 충족한 완료 기준은 카드에서 `- [x]`로 바꾼다. 충족하지 못한 기준이 있으면 게이트 대신 계속할지 묻는 것은 그대로다.
  - `lg`가 있으면 `lg verify --task <Task>`를 실행하고, 위반이 있으면 게이트 요청 전에 고친다(에이전트 스스로 고칠 수 없는 위반은 요청서 "예상과 달랐던 점"에 적는다).
- 6단계(보고): "판정은 터미널에서 `lg answer <review ID>`"를 보고 끝에 쓴다.

### 5.2 절차 escalate

- 4단계(보고): "응답은 터미널에서 `lg answer <review ID>`"를 쓴다.

### 5.3 `.claude/settings.json`

- deny에 `Bash(lg answer *)`를 더한다. 터미널 검사로 이미 막히지만 `lg commit`과 같게 둔다.

### 5.4 `scripts/apply-human-commits --preview`

- 표준 입력으로 커밋 메시지 하나를 받는다. 그 커밋이 반영되면 생길 상태 변화를 출력하고, 아무것도 쓰지 않는다.
- 지금의 계획 함수(`plan_for`)를 그대로 쓰고, 해시 자리에는 `(새 커밋)`을 쓴다.
- 반영할 수 없는 판정이면 코드 1과 이유를 낸다. 예: 카드가 `in-review`가 아님, 다음 카드가 `draft`가 아님. `lg answer`는 이것을 커밋 전에 보여 주고 멈춘다. 그래서 반영할 수 없는 판정이 커밋되는 일이 줄어든다.
- 미리보기가 프로젝트의 스크립트를 쓰므로 `lg`와 반영 규칙이 어긋나지 않는다.
- spec_version 2–4 프로젝트에는 이 옵션이 없다. 그때 `lg answer`는 미리보기 대신 trailer 요약만 보여 주고, `lg upgrade`를 권한다.

### 5.5 README 템플릿 (부록 A.1) "사람이 하는 일"

- `lg status`, `lg answer`를 쓴다.
- README는 연구 문서로 분류되므로(§22.3) 기존 프로젝트에서 `lg upgrade`가 바꾸지 않는다. 새 프로젝트에만 들어간다.

## 8. 결정이 필요한 것

| # | 질문 | 선택지 | 추천 |
|---|---|---|---|
| 1 | 명령 이름 | (a) `lg answer` (b) `lg review` (c) `lg judge` | **(a)**. `review`는 에이전트 전용 커밋 타입 `review(...)`(게이트 요청)와 이름이 같아서 "요청"으로 읽힌다. `judge`는 에스컬레이션 응답에 맞지 않는다. `answer`는 문서의 `## 응답`과 같은 말이다 |
| 2 | spec_version 5 범위 | (a) 올리지 않음(명령만, 미리보기 없음) (b) §5 전부 (c) (b) + 열린 세션 자동 감지 hook(UserPromptSubmit) + 커밋 순간 G3·G7 차단 | **(b)**. 미리보기가 1.1의 혼란을 직접 막고, 카드 체크는 이번에 실제로 겪은 문제다. (c)의 둘은 성격이 다르고(에이전트 쪽 강제) 실사용 근거가 아직 적으니 다음 마이너로 |
| 3 | 다음 task 여럿 | (a) gate + `plan` 두 커밋 (b) `Next`에 목록 허용(hook, 반영 스크립트, 사양 변경) | **(a)**. 커밋 규약을 바꾸지 않는다. 두 커밋은 도구가 만들므로 사람이 알 필요가 없다 |
| 4 | `respond` 커밋에 `Decisions` | (a) 허용하고 반영(반영 스크립트 변경, spec 5) (b) 허용하지 않음. 결정 확정은 따로 `decide` 커밋 | **(b)**. 지금 규약 그대로. 에스컬레이션에서 결정을 골랐으면 `lg answer`가 이어서 `decide` 커밋을 만든다(다음 task의 `plan` 커밋과 같은 방식) |
| 5 | `lg status`를 `session-check`에 연결 | (a) 연결하지 않음 (b) 세션 시작 보고에 `lg status --json` 사용 | **(a)**. `session-check`는 `lg` 없이 도는 것이 원칙이다(Python 3.9, 표준 라이브러리). 겹치는 정보는 이미 있다 |
