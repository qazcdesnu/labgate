# v0.3 설계 초안 — CLI 명령 설명서, 사용자 작업 설명서, 규칙 개정

> 상태: 초안 (검토 중). 확정되면 [labgate-design.md](../../labgate-design.md)에 병합하고 이 파일은 지운다.
> 전제: v0.2.1 (`main` 8341747). 이 초안은 v0.3.0의 세 파트(CLI 명령 설명서, 사용자 작업 설명서, 작업 목록과 규칙 개정)를 다룬다. ideation 사전 프로세스는 실사용 기록이 모인 뒤 별도 초안으로 쓴다.

---

## 1. 배경

v0.2.1을 실제 연구 프로젝트(`ssm-latent-reasoning`)에 처음 쓰면서 두 문제가 드러났다.

1. **규칙의 우선순위가 정의되어 있지 않다.** 첫 task 승인 뒤 세 문서가 서로 다른 말을 했다.

   | 위치 | 한 말 |
   |---|---|
   | `workflow.md` §1 원칙 2, §3 | 커밋이 우선이다. 상태 필드는 에이전트가 다음 커밋에서 반영한다 → **반영하라** |
   | `AGENTS.md` 규칙 6 | `draft → approved`는 절차 `gate-conversation`, `gate-apply`에서만 → **하지 마라** |
   | `session-start` 5단계 | 카드가 `approved`가 아니면 작업하지 않고 종료 → **멈춰라** |

   에이전트는 원칙을 택해 올바르게 반영했지만(`afbd430`, `Refs: 70ea21b`), 이는 문서가 아니라 에이전트의 판단에 기댄 결과다. 예외를 적는 방식도 세 가지(규칙 안의 괄호, 절차의 "푸는 일반 규칙", 원칙의 서술)로 섞여 있다.

2. **CLI의 사용 설명서가 없다.** 명령과 옵션의 설명은 `--help`와 설계 문서(구현자용)에만 있다. 사람이 쓰는 명령(`lg init`, `lg commit`)과 에이전트가 쓰는 명령(`lg draft`, `scripts/agent-commit`, `scripts/session-check`)의 경계도 한곳에 정리되어 있지 않다.

3. **사람이 하는 일의 안내가 없다.** "터미널을 두 개 띄우는가", "M0-T0은 어떻게 승인하는가", "세션을 이미 시작했으면 어떻게 하는가" 같은 질문이 실사용 첫날에 나왔다. 명령 설명서는 명령 단위라서 이런 작업 단위의 질문에 답하지 못한다.

## 2. 세 파트와 순서

| 파트 | 독자 | 단위 | 산출물 |
|---|---|---|---|
| **1. CLI 명령 설명서** | 사람·에이전트 | 명령과 옵션 | `docs/cli/` |
| **2. 사용자 작업 설명서** | 사람 | 사람이 하는 일 (승인, 판정, 직접 수정 …) | `docs/guide/` |
| **3. 작업 목록과 규칙 개정** | 에이전트 (규칙), 개발자 (작업 목록) | 에이전트의 작업(절차) | `docs/operations.md`, `AGENTS.md`·절차 문서 개정 |

**순서는 1 → 2 → 3.**
- 1이 먼저다. 2와 3이 명령을 설명할 때 명령 설명서를 가리키기만 하면 되도록, 명령의 사실(옵션, 동작, 읽고 쓰는 것, 종료 코드)을 한곳에 먼저 고정한다.
- 2가 3보다 먼저다. 사람의 작업 흐름을 순서대로 쓰다 보면 사람과 에이전트가 주고받는 지점(승인 커밋 → 에이전트의 반영 등)이 드러난다. 이번 빈틈(`plan`의 `Approve` 반영)도 사람의 "첫 task 승인" 흐름을 끝까지 따라가면 보인다.
- 3은 1·2를 근거로 한다. 특별 규칙은 "어떤 작업이 일반 규칙이 금지한 것을 해야 하는가"에서 나오므로, 사람과 에이전트의 모든 작업을 실행 주체와 바꾸는 대상으로 한 표에 놓는다(작업 목록). 이 표가 없으면 특별 규칙을 이번처럼 사고가 난 곳에만 덧대게 된다.
- 명령 설명서만으로 3을 정할 수는 없다. 특별 규칙은 명령이 아니라 에이전트의 작업 단위로 붙는다. `lg draft` 하나가 두 절차(`commit-prep`, `gate-conversation`)에서 쓰이고, 상태 반영(`gate-apply`)처럼 CLI 명령 없이 파일을 고치는 작업도 있다.

## 3. 파트 1: CLI 명령 설명서

### 3.1 문서 구성

labgate 저장소에 사용자용 문서를 둔다. 설계 문서는 구현자용 사양으로 남는다.

```
docs/
├── cli/
│   ├── README.md          # 명령 한눈에 보기: 누가, 언제, 무엇을 (§3.2 표)
│   ├── lg-init.md
│   ├── lg-commit.md
│   ├── lg-draft.md
│   └── project-scripts.md # 생성된 프로젝트의 scripts/agent-commit, scripts/session-check, commit-msg hook
├── guide/                 # 파트 2 (§4)
├── operations.md          # 파트 3의 작업 목록 (§5.1)
└── scenarios/             # (기존)
```

명령 문서마다 같은 형식을 쓴다.

```markdown
# lg <명령>

<한 줄 설명>

- 누가: 사람 | 에이전트 | 둘 다
- 언제: <쓰는 상황>
- 전제: <저장소, spec_version, TTY 등>

## 형식
## 인자와 옵션        (표: 이름 | 값 | 기본값 | 설명)
## 동작               (번호 목록, 설계 문서 해당 절 링크)
## 읽고 쓰는 것        (파일, stage, 커밋, tag)
## 종료 코드          (표)
## 예                 (자주 쓰는 경우 2–4개)
## 관련 절차          (에이전트 절차 문서 링크)
## 관련 작업          (사용자 작업 설명서 링크)
```

### 3.2 명령 한눈에 보기 (`docs/cli/README.md` 초안)

| 명령 | 누가 | 언제 | 바꾸는 것 |
|---|---|---|---|
| `lg init [PATH]` | 사람 | 프로젝트마다 한 번 | 파일 생성, Git 초기화, 사람 신원의 `init` 커밋 |
| `lg commit` | 사람 (터미널에서만) | 사람의 모든 커밋: 승인, 판정, 결정, 직접 고친 것 | stage(작성 모드에서 고른 파일), 사람 신원 커밋, tag, `.lg/pending/` 정리 |
| `lg draft` | 에이전트 (사람도 가능) | 사람 커밋의 초안을 준비할 때 | stage, `.lg/pending/COMMIT_MSG` |
| `lg --version` | 누구나 | | — |
| `scripts/agent-commit` | 에이전트 | 에이전트의 모든 커밋 | 에이전트 신원 커밋 |
| `scripts/session-check` | 에이전트 (Claude Code는 hook이 자동) | 세션 시작 | `.lg/pending/HUMAN_FILES` |
| `.lg/hooks/commit-msg` | Git이 자동 | 모든 커밋 | — (검사만) |

### 3.3 문서가 코드와 어긋나지 않게

- 테스트: Typer 앱의 모든 명령·옵션 이름이 해당 `docs/cli/lg-*.md`의 옵션 표에 있는지, 종료 코드 표가 `errors.py`의 상수와 같은지 검사한다.
- 설계 문서의 §5, §18, §19는 구현 사양으로 두고, 사용자용 설명은 `docs/cli/`가 맡는다. 중복되는 표(옵션, 종료 코드)는 위 테스트로 맞춘다.
- 테스트(파트 3 이후): `docs/operations.md`에서 "부딪치는 일반 규칙"이 있는 작업의 절차는 모두 특별 규칙 절을 가진다.

## 4. 파트 2: 사용자 작업 설명서

사람이 하는 일을 상황별로, 처음부터 끝까지 따라 할 수 있게 쓴다. 명령의 세부는 `docs/cli/`를 가리킨다.

```
docs/guide/
├── README.md            # 작업 고르기: "지금 무엇을 하려는가" → 문서
├── setup.md             # 설치, 프로젝트 만들기, 클론 후 설정, 터미널 두 개 (사람용·에이전트용)
├── daily-loop.md        # 세션 하나의 흐름: /session-start → 작업 → /task-gate → 판정
├── approve-task.md      # 첫 task 승인, 다음 task 승인 (lg commit --allow-empty, plan + Approve)
├── judge-gate.md        # 게이트 판정: 문서로 / 대화로 (lg commit, tag)
├── respond-escalation.md
├── edit-yourself.md     # 사람이 직접 고쳤을 때: 직접 커밋 / 에이전트 초안 / 세션 중 수정
├── change-plan.md       # 로드맵·마일스톤·사양 변경 (plan, spec 커밋)
├── mistakes.md          # 잘못된 커밋 되돌리기, 초안 버리기, 에이전트가 멈췄을 때
└── upgrade.md           # labgate 업데이트, 이전 버전 프로젝트의 규칙 문서 갱신
```

작업 문서마다 같은 형식을 쓴다.

```markdown
# <사람이 하려는 일>

- 언제: <이 문서가 필요한 상황>
- 결과: <끝나면 무엇이 남는가: 커밋, tag, 문서 상태>

## 순서        (터미널 A: 사람 / 터미널 B: 에이전트를 구분해 번호 목록)
## 확인        (끝난 뒤 확인할 명령과 기대 결과)
## 잘 안 될 때  (자주 막히는 지점과 해결)
## 에이전트는 무엇을 하나 (해당 절차 문서 링크)
```

**쓰면서 확인할 것:** 각 흐름에서 사람의 행동 다음에 에이전트가 이어받는 지점을 표시한다. 그 지점마다 에이전트 쪽 절차가 있고 일반 규칙과 부딪치지 않는지가 파트 3의 입력이 된다. 예: `approve-task.md`의 "승인 커밋 → 에이전트가 카드에 반영"은 `gate-apply`가 `plan`의 `Approve`를 다뤄야 함을 보여 준다.

실사용(`ssm-latent-reasoning`)에서 나온 질문을 각 문서의 "잘 안 될 때"에 넣는다.

## 5. 파트 3: 작업 목록과 규칙 개정

### 5.1 작업 목록 (`docs/operations.md` 초안)

모든 작업을 실행 주체와 바꾸는 대상으로 나열하고, 현재 일반 규칙(v0.2 `AGENTS.md` 번호)과 부딪치는지 표시한다. **부딪치는 작업이 특별 규칙이 필요한 곳이다.**

| # | 작업 | 주체 | 쓰는 도구 | 바꾸는 것 | 부딪치는 일반 규칙 |
|---|---|---|---|---|---|
| O1 | 프로젝트 초기화 | 사람 | `lg init` | 전체 | — |
| O2 | 사람 커밋 (승인·판정·결정·직접 수정) | 사람 | `lg commit`, `git commit` | 사람 신원 커밋, tag | — (사람의 일) |
| O3 | 세션 시작 점검 | 에이전트·hook | `session-check` | `.lg/pending/HUMAN_FILES` | 6 (`.lg/` 수정) |
| O4 | 이미 커밋된 초안 정리 | 에이전트 | 파일 삭제 | `.lg/pending/COMMIT_MSG` | 6 (`.lg/` 수정) |
| O5 | 사람 변경의 커밋 준비 | 에이전트 | `lg draft` | 사람 변경 stage, 초안 | 4 (사람 변경 stage), 6 (`.lg/`) |
| O6 | 대화 판정의 반영과 초안 | 에이전트 | 파일 편집, `lg draft` | review `## 응답`, 카드·결정 상태, 초안 | 6 (응답 작성, 상태 변경, `.lg/`) |
| O7 | **사람 커밋의 결과 반영** (gate, respond, **plan의 Approve**, **decide**) | 에이전트 | 파일 편집, `agent-commit` | review 이동, 카드·결정·마일스톤 상태 | 6 (사람 몫의 상태 전이, 결정 확정) |
| O8 | task 착수 | 에이전트 | `agent-commit` | 카드 `approved → in-progress` | — |
| O9 | 작업 수행 | 에이전트 | `agent-commit` | 코드·문서·실행 기록 | — |
| O10 | 게이트 요청 | 에이전트 | `agent-commit` | 결과 문서, review 생성, 카드 `in-review` | — |
| O11 | 에스컬레이션 | 에이전트 | `agent-commit` | review 생성, 카드 `blocked` | — |
| O12 | 세션 종료 | 에이전트 | `agent-commit` | 일지, STATUS | — |
| O13 | 변경 제안 | 에이전트 | `agent-commit` | `notes/`, 결정 `proposed` | — |

**이 표에서 나오는 결론:**
- 일반 규칙과 부딪치는 작업은 O3–O7이다.
- 그중 **정확하게 검증·실행할 수 있는 부분은 도구로 만든다**(§5.8): O3·O4는 `scripts/session-check`, O7의 상태 전이는 새 도구 `scripts/apply-human-commits`가 한다. 도구가 하는 일은 특별 규칙이 아니라 도구의 명세와 테스트로 정한다.
- 그래서 특별 규칙이 남는 곳은 에이전트가 판단해서 직접 하는 작업뿐이다: `commit-prep`(O5, 사람의 변경을 `lg draft`로 stage), `gate-conversation`(O6, 사람의 발언을 `## 응답`에 적기). 나머지 절차는 특별 규칙이 없다.
- 이번 사고는 O7의 범위가 v0.2에서 `gate`·`respond`로만 적혀 있어 `plan`의 `Approve`와 `decide`가 빠진 데서 생겼다. 표로 놓으면 바로 보이는 빈틈이다.


### 5.2 규칙의 층: 수정과 적용

규칙의 층은 두 축으로 본다. 법령에 빗대면 일반 규칙은 헌법이다. 개발(작업) 중에는 고칠 수 없고, 사람만 개정할 수 있다. 그러나 **적용할 때는** 법령과 마찬가지로 더 구체적인 규범이 먼저다: task 카드(특별법)가 가장 먼저, 그다음 절차의 특별 규칙(법률), 그다음 일반 규칙(헌법) 순이다.

**수정 축 (누가 언제 고치는가)**

| 층 | 위치 | 고치는 사람과 방법 |
|---|---|---|
| 불변 원칙 | `AGENTS.md` 1절 | 사람, `spec` 커밋 (labgate 버전과 함께 바뀌는 것이 원칙) |
| 일반 규칙 (헌법) | `AGENTS.md` 2절 | 사람, `spec` 커밋. 작업 중 에이전트는 고칠 수 없다 |
| 특별 규칙 (법률) | `specs/procedures/*.md` | 사람, `spec` 커밋 |
| task 카드 "범위 › 포함" (특별법) | `plan/milestones/<M>/tasks/<Task>.md` | 사람이 task 승인(`plan` + `Approve`, 또는 `gate`의 `Next`) 때 확정 |

**적용 축 (무엇이 먼저 적용되는가)**

| 순서 | 층 | 적용 범위 |
|---|---|---|
| 예외 없음 | 불변 원칙 | 항상. 어떤 층도 이를 풀 수 없다 (task 카드로도) |
| 1 | task 카드 "범위 › 포함" | 그 task를 수행하는 동안 |
| 2 | 절차의 특별 규칙 | 그 절차를 수행하는 동안 |
| 3 | 일반 규칙 | 위가 정하지 않은 모든 경우 |

불변 원칙을 일반 규칙과 따로 두는 이유: 사람 신원 커밋, 이력 재작성, 사람의 변경 폐기처럼 어기면 기록 자체가 거짓이 되는 것들이라, 적용에서도 구체적 규범이 풀 수 없어야 한다.

### 5.3 `AGENTS.md` 새 구성

```markdown
# 에이전트 작업 규칙
## 프로젝트
## 0. 규칙의 우선순위
## 1. 불변 원칙
## 2. 일반 규칙
## 3. 절차 (상황 → 절차 문서, 특별 규칙 유무)
## 참고
```

**0. 규칙의 우선순위 (문안)**

> 1. 불변 원칙은 무엇으로도 바뀌지 않는다. task 카드에 적혀 있어도 마찬가지다.
> 2. 현재 task 카드의 "범위 › 포함"에 명시된 것은 그 task를 수행하는 동안 특별 규칙과 일반 규칙보다 우선한다.
> 3. 절차를 수행하는 동안에는 그 절차 문서의 "특별 규칙"이 일반 규칙보다 우선한다. 특별 규칙은 그 절차 안에서만 유효하다.
> 4. 그 밖에는 일반 규칙을 따른다.
> 5. 문서끼리 충돌하거나 어느 규칙에도 없는 상황이면 불변 원칙에 맞는 쪽을 택한다. 그래도 정할 수 없으면 멈추고 사람에게 묻는다.

**1. 불변 원칙 (문안)**

> P1. 사실의 원본은 Git 커밋이다. 문서의 상태 필드는 커밋을 반영한 것이며, 둘이 다르면 커밋이 우선한다. 사람 커밋의 결과를 문서에 반영하는 것은 에이전트의 책임이다(절차 `gate-apply`).
> P2. 사람 신원으로 커밋하지 않는다. `git commit`, `lg commit`을 실행하지 않고, 커밋은 `scripts/agent-commit`으로만 한다(`--no-verify`, `--author`, `-a` 금지).
> P3. 사람 전용 커밋 타입(`gate`, `decide`, `plan`, `spec`, `respond`)을 쓰지 않는다.
> P4. 이력을 다시 쓰지 않는다(rebase, amend, force push). 브랜치를 병합하거나 cherry-pick하지 않는다. tag를 만들지 않는다.
> P5. 사람의 변경을 되돌리거나 치우지 않는다(`git restore`, `git checkout --`, `git stash`). 사람의 변경을 에이전트 커밋에 넣지 않는다.
> P6. 사람이 말하지 않은 판정·결정을 만들어 내지 않는다. 확인하지 않은 서지 정보나 수치를 지어내지 않는다.

**2. 일반 규칙 (문안, 괄호 예외 제거)**

> G1. 문서는 `specs/`의 사양을 따른다.
> G2. 자기가 바꾼 파일만 경로를 지정해 stage한다(`git add -A`, `.`, `-u` 금지). 사람의 변경은 stage하지 않고, 사람의 변경이 있는 파일은 고치지 않는다.
> G3. 사람 커밋 대기 상태(`.lg/pending/COMMIT_MSG` 있음)에서는 커밋하지 않는다.
> G4. 사람 몫의 상태 전이를 하지 않는다: task `draft → approved`, `in-review → closed | revise | redirected`, 결정 `→ confirmed`, 마일스톤 `planned → active → closed`.
> G5. review 문서의 `## 응답`을 쓰지 않는다.
> G6. `plan/roadmap.md`와 `active` 이상인 마일스톤의 목표·기준을 바꾸지 않는다. 변경은 `notes/`에 제안하고 `propose` 커밋.
> G7. `specs/`, `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.lg/`를 고치지 않는다. 변경은 `notes/`에 제안하고 `propose` 커밋.
> G8. 워크트리는 실험 격리용이다. 채택할 결과는 파일을 옮겨 새로 커밋한다.
> G9. 승인된 task의 범위·예산 안에서만 일한다. 넘어야 하면 멈추고 에스컬레이션한다(절차 `escalate`).
> G10. 본문은 한국어, 식별자·상태값·커밋 타입은 영어로 쓴다.

task 카드의 "범위 › 포함"은 0절 2항으로 옮긴다. 일반 규칙 안에 괄호 예외로 두지 않는다.

**3. 절차 표**에 "특별 규칙" 열을 둔다.

| 상황 | 절차 | 특별 규칙 | 쓰는 도구 |
|---|---|---|---|
| 세션 시작 | session-start | 없음 | `session-check` |
| 세션 종료 | session-close | 없음 | |
| 사람의 변경, 커밋 준비 요청 | commit-prep | 있음 (G2) | `lg draft` |
| 승인된 task 착수 | task-start | 없음 | |
| task 완료, 게이트 요청 | task-gate | 없음 | |
| 멈춤 조건 | escalate | 없음 | |
| 사람이 대화로 판정·결정·응답 | gate-conversation | 있음 (G5) | `lg draft` |
| 반영되지 않은 사람 커밋 | gate-apply | 있음 (G4) | `apply-human-commits` |

### 5.4 절차 문서의 특별 규칙 형식

"푸는 일반 규칙" 줄을 없애고, 머리 아래에 절을 둔다.

```markdown
## 특별 규칙

이 절차를 수행하는 동안 아래가 일반 규칙보다 우선한다. 불변 원칙은 그대로다.

| 대신하는 일반 규칙 | 이 절차에서는 |
|---|---|
| G4 (사람 몫의 상태 전이 금지) | 사람 커밋의 trailer가 정한 전이를 상태 필드에 반영한다. trailer에 없는 전이는 하지 않는다. |
```

특별 규칙이 없는 절차는 "## 특별 규칙\n\n없음. 일반 규칙을 따른다."로 명시한다.

### 5.5 특별 규칙 (문안)

도구가 하는 일(파일 기록, 상태 전이, 초안 쓰기)은 특별 규칙으로 허용하지 않고 도구 명세로 정한다(§5.8). 특별 규칙은 에이전트가 직접 하는 일에만 둔다.

| 절차 | 대신하는 일반 규칙 | 이 절차에서는 |
|---|---|---|
| commit-prep | G2 | 사람의 변경을 stage할 수 있다. 단, `lg draft`를 통해서만 |
| gate-conversation | G5 | 사람의 발언을 그대로 `## 응답`에 적는다. 사람이 말하지 않은 내용을 더하지 않는다 |
| gate-apply | G4 | 사람 커밋이 정한 상태 전이를 커밋한다. 전이는 `scripts/apply-human-commits`가 만든 것만 쓰고, 상태 필드를 직접 편집하지 않는다 |

v0.2와 달라지는 점:
- `session-start`는 특별 규칙이 없어진다. `.lg/pending/` 기록과 이미 커밋된 초안 정리를 `session-check`가 한다.
- `gate-conversation`은 상태 전이를 하지 않는다. 사람 커밋의 trailer만 초안에 넣고, 사람이 커밋한 뒤 `gate-apply`가 도구로 반영한다. 그래서 대화 경로와 문서 경로가 같은 반영 경로를 쓴다.

### 5.6 이번 빈틈의 수정

- `gate-apply`의 시작 조건: "상태 필드에 반영되지 않은 사람 커밋이 있을 때". 반영 대상 표를 둔다.

  | 사람 커밋 | 반영 |
  |---|---|
  | `gate` | review 닫기, 카드 `Verdict`대로, `Next` 카드 `approved`, `Milestone-Verdict`면 마일스톤 |
  | `respond` | review 닫기, 카드 `blocked → in-progress` |
  | `plan` + `Approve` | 해당 카드 `draft → approved` |
  | `decide` | 결정 `→ confirmed` |

- `session-start`: 현재 task 카드의 상태를 판단하기 **전에** "반영되지 않은 사람 커밋이 있으면 `gate-apply`"를 둔다.
- `task-start` 1단계: 카드가 `draft`이고 반영되지 않은 `Approve`가 있으면 `gate-apply`를 먼저 한다.
- 반영 커밋의 trailer에 `Applies: <사람 커밋 해시>`를 남긴다. 이번에 에이전트가 스스로 `Refs:`로 남긴 방식을 전용 trailer로 고정해, 도구가 "반영되었는가"를 정확히 판별하게 한다(§5.8).
- 이 표의 전이는 `scripts/apply-human-commits`가 수행한다.

### 5.7 `workflow.md`

원칙 서술(§1)은 `AGENTS.md`의 불변 원칙을 가리키게 하고, 같은 문장을 두 곳에 두지 않는다. 상태 기계(§3)의 "기록하는 커밋" 열에 반영 경로(`gate-apply`)를 명시한다.

### 5.8 코드 우선 원칙

**정확하게 검증하고 실행할 수 있는 일은 문서 규칙이 아니라 코드(스크립트·도구)로 만든다.** 에이전트의 해석에 맡기는 것은 판단이 필요한 일(문장 작성, 선택지 비교, 멈출지 결정)뿐이다. 도구는 테스트로 동작을 고정한다.

| 일 | v0.2 | v0.3 |
|---|---|---|
| 사람의 변경 감지·기록 | `session-check` | 그대로 |
| 반영되지 않은 사람 커밋 감지 | 에이전트가 문서를 보고 판단 | `session-check`가 감지해 알림 |
| 이미 커밋된 초안 정리 (O4) | 에이전트가 `git log`와 비교해 삭제 | `session-check`가 같은 헤더의 사람 커밋을 찾으면 삭제 |
| 상태 전이 반영 (O7) | 에이전트가 상태 필드를 편집 | `scripts/apply-human-commits` |
| 사람 커밋 초안 쓰기 | `lg draft` | 그대로 |

**`scripts/apply-human-commits` (새 도구, Python 표준 라이브러리, `lg` 불필요):**
- 감지: 사람 커밋 중 반영 대상 trailer(`Verdict`, `Approve`, `Decisions`+`decide`, `respond`)가 있고, 그 해시를 `Applies:`로 가리키는 에이전트 커밋이 아직 없는 것.
- 동작: §5.6 표의 전이를 frontmatter `status`와 마일스톤 task 목록 표에 적용하고, review 문서를 `reviews/closed/`로 옮긴다(`git mv`). 카드의 "게이트 이력"에 판정과 해시를 한 줄 추가한다.
- 출력: 바뀐 파일 목록과, 에이전트가 쓸 커밋 메시지 초안(`log(<Task>): apply <해시>` + `Applies: <해시>`). 커밋은 에이전트가 `scripts/agent-commit`으로 한다(도구는 커밋하지 않는다).
- `--check`: 바꾸지 않고 반영 대상만 출력한다. `session-check`가 이것을 쓴다.
- 반영할 수 없는 경우(카드 파일 없음, 현재 상태가 전이의 출발 상태와 다름)는 바꾸지 않고 이유를 출력하며 0이 아닌 코드로 끝난다. 에이전트는 멈추고 사람에게 묻는다.
- commit-msg hook은 `Applies` trailer의 형식(커밋 해시)을 검사한다.

## 6. 버전과 호환성

- **spec_version 3.** 생성되는 규칙 문서의 의미가 바뀐다(우선순위, 특별 규칙).
- **`lg commit`·`lg draft`는 spec_version 2와 3을 모두 지원한다.** 커밋 규약(hook의 타입·trailer)은 바뀌지 않으므로 v0.2 프로젝트를 거부할 이유가 없다. 현재 `project.py`는 `SPEC_VERSION`과 같은지만 보므로 "지원 목록"으로 바꾼다.
- **v0.2 프로젝트의 규칙 문서 갱신**은 `lg upgrade`가 없는 동안 수동이다: 새 `AGENTS.md`와 `specs/procedures/`를 사람이 복사하고 `spec` 커밋. `ssm-latent-reasoning`이 첫 대상이다. 이 수동 절차는 `docs/guide/upgrade.md`에 적는다.

## 8. 결정된 사항

1. "범위·예산 안에서만 일한다"(G9)는 일반 규칙에 둔다.
2. 일반 규칙은 헌법처럼 작업 중에 고칠 수 없고 사람만 개정한다. 적용할 때는 task 카드 "범위 › 포함" > 절차의 특별 규칙 > 일반 규칙 순으로 구체적인 것이 먼저다(§5.2). 불변 원칙은 적용에서도 예외가 없다.
3. `docs/cli/`는 당분간 labgate 저장소에만 둔다. 에이전트가 링크로 참조하기 어렵다면 생성된 프로젝트에 넣는 것을 검토한다. 이는 별도로 꼼꼼히 설계한다.
4. 정확하게 검증·실행할 수 있는 일은 코드로 만든다(§5.8). "반영되지 않은 사람 커밋" 감지는 `session-check`가 한다.

## 9. 열린 질문

1. `apply-human-commits`를 `session-check`와 같은 파일의 하위 명령으로 둘 것인가, 별도 스크립트로 둘 것인가. 감지 로직을 공유하므로 공용 모듈(`.lg/lib/`)이 필요할 수 있다.
2. 도구가 커밋까지 할 것인가. 초안은 에이전트가 확인하고 `agent-commit`으로 커밋하게 했다(에이전트 신원 고정, 결과 확인 기회).
3. 3-4 단계에서 v0.2 프로젝트(`ssm-latent-reasoning`)에 새 도구를 넣는 방법. `lg upgrade`가 없으므로 수동 복사와 `spec` 커밋으로 한다.
